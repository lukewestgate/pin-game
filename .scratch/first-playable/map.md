# Map: Peg Game, first playable

Label: wayfinder:map

## Destination

A buildable spec for the **first playable version**: the full Box/Buffer sorting rules plus **one** car Model, playable as a mobile-first PWA (touch first, mouse always works) in the target look. Alongside it, a short **vision** of the final game, so the first version is built to extend (more levels, procedural levels, boosters). When the map is clear, hand off to `/to-spec`.

## Notes

- Vocabulary: use `GLOSSARY.md` (Pin, Box, Capacity, Buffer, Level, Model, Part, Socket, Core, Blocked, Peek). Grilling tickets also call `/domain-modeling`.
- Settled while charting (the baseline every ticket assumes):
  - **Distribution:** installable PWA, no app stores for now. Portrait, mobile-first; desktop mouse must always work.
  - **Controls:** drag rotates the Model around its centre. Tap or click removes a Pin. Pinch or the scroll wheel zooms. No panning. A deliberate press-and-hold on a Part starts **Peek** (only that Part turns see-through). While Peeking, dragging still rotates; releasing ends Peek. Peek never changes game state.
  - **Numbers:** Box count, Capacity, Buffer size and colour count are developer constants, with optional per-level overrides. They must stay tweakable so they can drive later hardness sliders. Defaults: see Sorting rules logic prototype.
  - **Boxes:** never two open Boxes of the same colour. A removed Pin goes to the matching open Box, otherwise to the Buffer. The level is lost the moment a Pin fills the last Buffer slot. When a Box closes, the replacement takes a colour that still has Pins left (on the Model, Blocked or not, or in the Buffer) and has no open Box, preferring reachable colours (see Sorting rules logic prototype). Matching Buffer Pins then drain into it. A position with no qualifying colour shows grey (end of level). Choices are seeded per level, so levels are deterministic.
  - **Pins and Parts:** a Pin is Blocked while any Part covering it is still present, as written in the level data (not decided by what the camera can see). A Part falls away once all its Pins are removed.
  - **Win:** every Pin removed. Each colour's Pin total is a multiple of Capacity.
  - **Winnability:** every level (hand-made or generated) must have at least one winning tap order, checked by a solver. Difficulty = how hard that order is to find.
  - **In the first version:** unlimited undo as a debug tool, plus animations for Pin → Box or Buffer, Buffer → Box, Box close and next Box slide-in, and Part falling away (scripted, no physics). Sound: small effects only, no music (decided in Sound in the first version).
  - **Generator-friendly:** the level format must be something a procedural generator could produce later, even though no generator ships now.
- The game's name is **Pin Game** (decided in PWA hosting, caching and updates). The folder and this map still say "peg game".
- The user knows TypeScript/JS, C# and GDScript, and has used Blender.
- Research findings live in `.scratch/first-playable/research/` and prototypes in `.scratch/first-playable/prototypes/`, instead of throwaway branches.

## Decisions so far

<!-- one line per closed ticket: [title](issues/NN-slug.md): gist -->

- [Engine options for a mobile-first 3D PWA](issues/01-engine-options-for-mobile-pwa.md): the strongest candidates are Three.js+TS (smallest), Babylon.js+TS (most built in, headless engine for tests) and Godot 4.7+GDScript (best editor, but iOS risk and multi-MB WebAssembly). Unity is the weakest fit. Peek's hold gesture is custom code in every engine.
- [Achieving the clean cartoon look on mobile web](issues/02-clean-cartoon-look-on-mobile.md): smooth normals plus about 32-segment wheels and 12–16-segment Pins, toon or Lambert shading, inverted-hull outlines, 4× MSAA with DPR capped at about 2, instanced Pins. Peek needs a depth pre-pass. Babylon has the most built in, Godot web the least.
- [Solver approaches for checking that levels can be won](issues/03-solver-approaches-for-winnability.md): a depth-first search over tap orders that remembers visited states is enough. The colour rule must be a pure function of the seed. With colours ≤ Boxes every level is trivially winnable, so colour count against Box count and Buffer size is the main difficulty knob.
- [Sorting rules logic prototype](issues/04-sorting-rules-logic-prototype.md): defaults are 3 Boxes / Capacity 3 / Buffer 5, and every number stays tweakable for later hardness sliders. You lose the moment the last Buffer slot fills. The next Box prefers colours that are reachable now. The next-Box preview is a dev option only. Start the first car at about 5 colours. The prototype's rules module can be lifted into the real engine.
- [How Models and Parts are built](issues/05-how-models-are-built.md): Models are JSON made of primitive shapes (no Blender for now). A Model (Parts, Sockets, covering) is separate from a Level (explicit Socket colours, seed, overrides). Covering is hand-written and checked by a ray-based dev warning. Authoring is hand-written JSON plus a dev viewer.
- [Tech stack](issues/06-tech-stack.md): Babylon.js + TS on WebGL2, Vite + pnpm, Vitest, Zod, strict TS with ESLint. One package with lint-enforced pure `rules`/`solver`/`content`. `tap()` returns state plus events that rendering plays. Boxes and Buffer are drawn in the scene by an orthographic camera. The solver runs in a Web Worker in the dev viewer. See ADR 0002.
- [Car level design](issues/07-car-level-design.md): a chunky hatchback in neutral colours with 30 Pins. 16 outer Pins sit on the wheels, bonnet, roof, doors, tailgate and a spare wheel. 14 inner Pins sit on the axles, engine, seats and steering wheel, each behind one Part. The Cores are the chassis, bumpers and headlights, and a Part can now have several shapes (ADR 0001 amended). 5 colours × 6, 3 Boxes / Capacity 3 / Buffer 6 as an override. Target: solver-proven and a 60–80% random-tap win rate (meant to feel easy). Colours are dealt by a seeded script, then frozen.
- [Vision of the final game](issues/08-vision-of-the-final-game.md): a relaxed hand-made Campaign that ramps gently (a random spread of Models, many Levels per Model, optional Packs), plus Endless mode with hardness sliders. Boosters are pure rules actions like `tap`. The next-colour rule is a swappable strategy (a future `queue` variant gives a truthful preview). Saving goes through a local progress store interface. A separate level editor shows live difficulty. Twelve extension points are in [vision.md](vision.md).
- [Animation sequencing and input during animations](issues/09-animation-sequencing-and-input.md): rapid tapping never slows down. Taps go to the rules at once and animations overlap. A pure `Timeline` scheduler times each step to the Box slot or Buffer it touches, so a Pin pulls out immediately and hovers if its Box is still closing. Blocked is judged on the rules state. Undo snaps. Default timings are recorded on the ticket.
- [Checks in the toolchain](issues/10-checks-in-the-toolchain.md): a Vitest test requires every level in `data/levels/` to be solver-proven, and *unknown* fails. `pnpm build` runs `pnpm check` (typecheck, lint, tests, Prettier) first, with no hook or CI yet. `pnpm solve` and the dev viewer show the report, which includes a seeded random-tap win rate. The 60–80% band never blocks, but each level's report is snapshotted, and the first snapshot must match the prototype. The ticket lists what the rules, content, Timeline, render and input tests cover.
- [PWA facts for Vite and iOS](issues/14-pwa-facts-for-vite-and-ios.md): `vite-plugin-pwa` 2.0.0's `generateSW` precaches JS, CSS and HTML by default (add `json` for loose data files, 2 MiB per-file cap). `prompt` is the default; `autoUpdate` reloads tabs mid-level. iOS can't lock portrait, has open status-bar and safe-area bugs on 26.1+, and ignores `user-scalable=no`, so use `touch-action`. Android needs 192 and 512 px icons plus a separate maskable one. GitHub Pages sends a fixed `max-age=600` and allows no custom headers. Cloudflare and Netlify allow `_headers`, and Netlify charges credits per deploy.
- [Screen layout and HUD](issues/11-screen-layout-and-hud.md): portrait layout with the Box row and then the Buffer at the top, the Model in the middle, and dev Undo and Restart in a bottom bar. Boxes are roughly square, with their slots in two rows (Capacity 3 gives 2 + 1). Buffer Pins are drawn at 0.8 the size of Box Pins. The design target is 360 × 640, and everything reflows from the level's numbers. The HUD camera works in CSS px with the safe-area insets applied. Landscape and desktop get a centred portrait column (landscape isn't really supported). The car's bounding sphere is fitted to its region, with zoom from 1× to 2.2×.
- [Pin colours and colour-blind readability](issues/12-pin-colours-and-colour-blind-readability.md): the **Candy** palette, bright toy colours in the spirit of the inspiration but with original values. In order: red, yellow, green, blue, pink, then orange, purple, cyan, white and black. The car uses the first 5. With normal vision every colour reads clearly up to 10. Every Pin head has the same cross recess (Head mark). A colour-blind setting, off by default, gives each colour its own drive recess (cross, slot, hex, Torx, square, triangle), from one atlas with a per-instance index. Pin head form and where the setting is switched go to UI visual style.
- [Gesture tuning](issues/13-gesture-tuning.md): a pure `gestureStep` classifier and `pickPin` picker, ready to lift into `src/input`. Hold for Peek is 240 ms and a drag starts after 10 px (4 px for a mouse). Tap targets are max(head × 1.6, 36 px), and a missed tap takes the nearest tappable Pin within 18 px. Turning is a turntable at 200° per Model-region width. A second finger turns any gesture into a pinch, and the finger left after a pinch is ignored. The ticket lists the feedback timings. Starting values, to be tuned in the build.
- [PWA hosting, caching and updates](issues/15-pwa-hosting-caching-and-updates.md): the game is named **Pin Game**. It's hosted on GitHub Pages from a public `pin-game` repo, with CI added alongside the remote: deploy on every push to `main`, and `pnpm check` on PRs. It precaches everything with no network use while playing. Updates use `prompt` mode and are applied silently at a safe moment (no taps yet, or a win/lose banner showing), never mid-level. The iOS status bar uses `default` because of the inset bug (ADR 0003). Touch, overscroll and callout fixes ship now. `storage.persist()` waits for saved progress. The ticket lists the manifest and icons, plus a manual device checklist.
- [Sound in the first version](issues/16-sound-in-the-first-version.md): sound is in but small. Short CC0 effects (mono MP3, about 200 KB, precached), no music, and the game plays the same without audio. Sounds start with their `Timeline` steps, so a Buffer landing sounds duller than a Box landing, and seating Pins climb a chord per Box. Each sound has a voice cap of about 4. Undo cancels pending sounds. A mute toggle is remembered in a `localStorage` settings store, which the colour-blind setting shares. AudioEngineV2 unlocks on the first `pointerup`, with `audioSession` set to `ambient`. The iOS checks are on the device checklist.
- [Screwdom 3D visual style](issues/18-screwdom-3d-visual-style.md): the inspiration is a soft vinyl-toy look. Muted bevelled Models with no ink outlines and Lambert-like shading, where only the Pins and Box rims are saturated, on a pale plain gradient. Pins are domed, flush discs. Boxes are chunky tinted rims around neutral recessed holes. The HUD uses fat outlined type and candy buttons. The game shows no visible Buffer warning. 15 qualities to carry over in original art feed UI visual style.
- [UI visual style](issues/17-ui-visual-style.md): style **Workbench**, painted tin trays on a dark slate vignette (CSS behind a transparent canvas). 3-band toon shading, ink outlines on the Pins only, renderer-side bevels. Pan-head Pins with a recessed Head mark and a shank shown on pop-out. Solid tinted tin Boxes with dark holes. A rubber-mat Buffer that shows amber rings with 2 slots left and a red pulse on the last. Baloo 2 type, teal pill buttons with in-house SVG icons. The colour-blind switch sits in a settings sheet beside Mute. Win and lose ribbons slide in. `theme_color` `#34505b`. The iOS `default` status bar over a dark scene goes on the device checklist.
- [Car Model toy look](issues/19-car-model-toy-look.md): the car is a **wooden toy**: a grained wood body with mudguards and dowel pillars, axles and bumpers, wooden hubs in rubber tyres, and each outer plate painted its own muted tint (slate bonnet, rose roof, sage doors, lilac tailgate). Parts, Socket counts and covering are unchanged, so the Level still holds. Doors are shorter and one tailgate Socket moved. The new car colours replace UI visual style's. ADR 0001 gains an optional per-shape `round` and `finish: "wood"`. Starts in a front three-quarter view from above.

- App store builds and native wrappers (Capacitor/Tauri). Vision only.
- A procedural level generator. Vision only; the first version only keeps the format generator-friendly.
- Player-facing limited undo, boosters, hints, timers. Vision only.
- More than one level, level select, progression, saved progress, monetisation. Vision only.
- The level editor (a separate Vite entry with live difficulty), Campaign and Pack files, Endless mode, accounts, and a progress store backed by the cloud. Vision only, see [Vision of the final game](issues/08-vision-of-the-final-game.md). The first version only keeps their extension points open.
